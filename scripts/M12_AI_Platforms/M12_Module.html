Section 1 · Reading — ~5 min

The Spark: Platforms, Not Just Models

Competition drives innovation. In AI, competition drove an entire ecosystem. Google, OpenAI, and Anthropic did not just build better models. They built platforms. And knowing how to work across them is what makes you versatile.

Think about the arc this course has taken. Early on, you sent a prompt to a model and got an answer back. One request, one response. Then you gave the model tools and memory and turned it into an agent that could act, not just talk. In Module 11 you connected an agent to your tools and data through MCP and drove real work with Claude Code. The natural next step is more than one agent. Once you have several specialized agents, something has to coordinate them, and that coordination layer is the platform.

Modelanswers a prompt
→
Agentmodel + tools + memory
→
Many agentscoordinate on a task
→
Platformthe layer that connects them
Figure 1. The capability ladder: why a coordination layer becomes necessary.

Two Problems Every Platform Solves

Strip away the branding and every agent platform is answering one of two questions. The first is how does an agent reach its tools and data? That is the problem MCP solved in Module 11: a standard way to plug an agent into files, APIs, and databases. The second is how do agents reach each other? When your team builds a research agent and another team builds an analysis agent, in different frameworks, running on different servers, they need a shared way to discover one another and exchange work. That is the problem the Google A2A protocol solves.

Alongside those connection problems sits a build problem: even with tools and protocols available, you still have to assemble one agent application and get it into production. That is where an agent SDK comes in. The OpenAI Agents SDK gives you a clean Python interface for defining agents, wiring them together, and shipping them with safety checks in place.

Two Philosophies

The two platforms in this module reflect two ways of thinking. Google thinks in protocols: open standards that let any agent talk to any other agent, regardless of who built it. OpenAI thinks in SDKs: a small, opinionated toolkit that lets you build a working multi-agent app fast. Same destination, different roads. By the end of this module you will have seen both, and you will understand when to reach for each.

Where this sits. Module 12 comes right after M11 (MCP and Claude Code) and feeds directly into the Final Project, where you assemble everything into a working system. Keep MCP in mind as you read: it is the third piece of the puzzle we tie together on the "How It Fits" page.

Section 2 · Reading — ~8 min

The Google A2A Protocol

A2A stands for Agent-to-Agent. It is an open protocol that Google announced in April 2025 and later donated to the Linux Foundation for vendor-neutral governance. Its job is to let agents built by different teams, in different frameworks, running at different companies, find each other and collaborate.

The Problem: Siloed Agents

Right now, if you build an agent in CrewAI, it naturally talks only to other CrewAI agents. If someone else builds an agent in LangGraph, those two systems cannot collaborate without custom glue code written by hand for that one pairing. Multiply that across an enterprise with dozens of teams and you get a combinatorial mess: every new agent needs a bespoke integration with every other agent it should talk to. That does not scale.

Think about what HTTP did for the web. Before HTTP, every network had its own protocol and browsers could not talk to arbitrary servers. After HTTP, any browser could talk to any server. A2A aims to be that shared layer for AI agents: implement the spec once, and your agent can discover, message, and delegate to any other A2A-compatible agent. Google did not build it alone, either. The protocol launched with more than fifty technology partners, including Salesforce, SAP, LangChain, and CrewAI, and the spec is open for anyone to implement.

The Three Building Blocks

A2A has a small surface area. Three concepts carry the whole protocol.

Agent Cardcapabilities + endpoint
+
Taskthe work to be done
+
TransportHTTP · SSE · JSON-RPC
Figure 2. The three building blocks of A2A.

An Agent Card is like a business card for an AI agent. It is a JSON document, hosted at a well-known URL, that describes what the agent can do, what inputs it expects, and what authentication it requires. When another agent wants to find a collaborator, it reads the Agent Card first. A Task is the unit of work agents exchange: a structured request with a clear goal, sent to a discovered agent. The receiving agent processes it and returns results, either all at once or as a stream of progress updates. The transport layer is deliberately built on boring, proven web technology: requests go over plain HTTP, use JSON-RPC 2.0 for structured calls, and use Server-Sent Events (SSE) for streaming. There is nothing exotic here, which is exactly the point. Any engineer who knows web APIs can implement it.

Inside an Agent Card

An Agent Card is just JSON, but the shape is what makes discovery work. It advertises a name and description so a human or another agent can tell what it is, a service url to send tasks to, the list of skills it offers, and the authentication it expects. A calling agent fetches this document from /.well-known/agent.json, reads the skills, and decides whether this is the right collaborator, all before sending a single unit of real work.

Figure 3. An A2A Agent Card: name, service URL, advertised skills, streaming capability, and auth scheme. A calling agent reads this before sending any task.

The Flow, End to End

1
Discoverread Agent Card/.well-known/agent.json
2
Send Taskstructured requestPOST /tasks
3
Streamprogress updatesSSE
4
Resultfinal outputdone
Figure 4. The A2A flow: discover the Agent Card, send a Task, receive streamed updates, get the result.

Streaming matters more than it looks. Many agent tasks take real time, searching, reasoning, calling other systems, and the calling agent needs to know what is happening rather than staring at a frozen request. SSE lets the worker agent report progress as it goes.

A Task Has a Lifecycle

A Task is not fire-and-forget. It moves through a defined set of states, and the worker agent reports each transition back over the stream. A task is submitted, then working while the agent labors, and it may pause at input-required if it needs more information from the caller. It ends in one of three terminal states: completed, failed, or canceled. Because the states are standardized, the calling agent can build reliable logic around them without knowing anything about how the worker is implemented.

Figure 5. A2A task lifecycle. A task moves from submitted to working (optionally pausing at input-required) and ends in one terminal state: completed, failed, or canceled.

Why It Matters

The real value of A2A is interoperability. Your CrewAI research agent publishes an Agent Card. Someone else's LangGraph analysis agent reads that card, sends a Task, and gets results back. Neither team wrote code specific to the other. The frameworks stop mattering; the protocol handles the translation. This is how enterprise AI is likely to work at scale: not one company building every agent, but many teams building specialized agents that discover and collaborate through a shared standard.

Section 2 · Reading — ~5 min

A2A in Practice: Discovery and Delegation

The building blocks are simple. Watching them work together end to end is what makes the protocol click. Here we walk one delegation from the calling agent's point of view, then look at the actual messages on the wire.

The Two Roles

Every A2A exchange has two roles. The client agent is the one that needs work done: it discovers a collaborator, frames the goal as a Task, and consumes the result. The remote agent is the one that does the work: it publishes an Agent Card, accepts Tasks, and streams progress back. A single agent can play both roles at different moments, a client to one agent and a remote to another, which is how larger networks of agents form.

Figure 7. One A2A delegation, message by message: discover the card, send a task, stream progress, receive the completed result.

The Messages on the Wire

Because A2A rides on JSON-RPC over HTTP, the actual request is unremarkable, which is the whole point. A client sends a tasks/send call with the goal; the remote answers with a task id and a status that later flips to completed.

# Client -> remote: send a task (JSON-RPC 2.0 over HTTP)
POST /a2a  HTTP/1.1
{
  "jsonrpc": "2.0", "id": "1",
  "method": "tasks/send",
  "params": {
    "id": "task-42",
    "message": { "role": "user",
      "parts": [{ "text": "Summarize the A2A spec" }] }
  }
}

# Remote -> client: task accepted, then streamed to completed
{ "jsonrpc": "2.0", "id": "1",
  "result": { "id": "task-42", "status": { "state": "completed" } } }

Nothing here is agent-specific. Any engineer who has called a REST API can read this exchange. That familiarity is deliberate: A2A chose proven web plumbing so adoption would not require learning a new transport.

Section 3 · Reading — ~8 min

The OpenAI Agents SDK

Where A2A is a protocol for connecting agents, the OpenAI Agents SDK is a toolkit for building one. It is a lightweight Python framework (the production successor to OpenAI's experimental "Swarm") with a deliberately tiny surface area: a small number of powerful primitives that you compose into whatever you need.

Why Minimalism Is the Point

Earlier agent frameworks asked you to learn a large vocabulary of concepts before you could ship anything. The Agents SDK takes the opposite bet. It gives developers just a few primitives and leans on plain Python for everything else, so the learning curve is shallow and the code stays readable. If you know Python functions and classes, you already know most of what you need.

Four Building Blocks

Agentmodel + instructions
↔
Toolscall functions
↔
Handoffsdelegate to a specialist
↔
Guardrailsvalidate in / out
Figure 8. The anatomy of an OpenAI Agents SDK application.

An Agent is a language model configured with instructions and a set of tools. The instructions shape its behavior; the tools give it the ability to act. A Tool is simply a Python function the agent is allowed to call, decorated so the SDK knows its name and arguments. When the agent decides it needs to search, calculate, or fetch something, it calls the matching tool and works with the result.

Figure 9. Tools flow. The @function_tool decorator exposes a plain Python function; the agent calls it, the function reaches an external system, and the result flows back into the agent's reasoning.

A Handoff lets one agent delegate to another. Rather than one giant do-everything agent, you build small specialists, a researcher, a writer, an analyst, and let a coordinating agent transfer control to the right one at runtime. Guardrails are input and output checks that run alongside the agent and fail fast. An input guardrail can reject an off-topic or unsafe request before the agent spends tokens on it; an output guardrail validates the final answer before it reaches the user. Guardrails apply to the boundaries of a run: input guardrails to the first agent that receives the request, output guardrails to the agent that produces the final answer.

The Smallest Complete Example

Because the surface area is so small, a working agent is only a few lines. You define an agent with a name, instructions, and tools, then hand it to the Runner, the execution engine that runs the agentic loop and returns a result.

from agents import Agent, Runner, function_tool

# A tool is just a decorated Python function
@function_tool
def search(query: str) -> str:
    """Search the web for a query and return results."""
    return run_search(query)

# An Agent = model + instructions + tools
agent = Agent(
    name="Researcher",
    instructions="Find and summarize recent, credible sources.",
    tools=[search],
)

# The Runner drives the loop and returns the result
result = Runner.run_sync(agent, "Find recent papers on the A2A protocol")
print(result.final_output)

Runner is the fourth verb. Agent, Tool, and Handoff describe what your system is. The Runner is how it executes: it takes an agent and an input, runs the tool-calling and handoff loop until the task is done, and hands you back the final output.

The Agent Run Loop

The Runner does not call the model once. It runs an agentic loop: the model may respond with a tool call, the Runner executes the tool, feeds the result back, and calls the model again. This repeats until the model returns a final answer with no more tool calls, at which point the loop stops and the output is returned. A handoff is just a special outcome of one turn: instead of finishing, control transfers to another agent and the loop continues with that agent.

Figure 10. The Runner's agentic loop. Call the model, run any requested tool or handoff, feed the result back, and repeat until the model returns a final output.

Section 3 · Reading — ~6 min

The Handoff Pattern

Handoffs are the SDK's signature idea, and the reason it feels different from earlier multi-agent frameworks. Instead of choreographing an entire crew up front, each agent simply declares which other agents it can hand off to, and the routing happens dynamically at runtime.

A Triage Agent Routes the Work

The canonical pattern is a triage agent that receives every user request and decides which specialist should handle it. A research agent searches the web. A writing agent drafts prose. An analyst agent runs calculations. The triage agent inspects the request and hands off to the right specialist. The Runner manages the execution loop until the task is complete.

Triage Agentreads the request, routes it
Researchertools: [search]
Writertools: [draft]
Analysttools: [calculate]
Figure 11. A triage agent hands off to whichever specialist fits the request. Routing is decided at runtime, not hard-wired.

Why Dynamic Routing Beats a Fixed Crew

In a fixed-crew framework you specify the whole workflow ahead of time: this agent, then that agent, then that one. That works when the path is always the same. But real requests are messy. Some need research, some need only formatting, some need a calculation and nothing else. With handoffs, the triage agent decides at runtime which specialist gets the job, so the same system handles a wide range of requests without you enumerating every path.

from agents import Agent, Runner

researcher = Agent(name="Researcher", instructions="Search and summarize.", tools=[search])
writer     = Agent(name="Writer",     instructions="Draft clear prose.")

# The triage agent declares who it can hand off to
triage = Agent(
    name="Triage",
    instructions="Route research questions to the Researcher, writing to the Writer.",
    handoffs=[researcher, writer],
)

result = Runner.run_sync(triage, "Summarize the A2A spec, then write a one-paragraph intro.")

Handoffs stay inside one run. Control moves from agent to agent, but it is still a single execution. That is why the input guardrail applies only to the first agent in the chain and the output guardrail only to the agent that produces the final answer, a useful detail when you start adding safety checks.

Where Guardrails Sit

Guardrails wrap the boundaries of a run, not every agent in the middle. An input guardrail runs on the first agent that receives the request and can trip a tripwire that halts the run before any tokens are spent, useful for rejecting off-topic or unsafe input early and cheaply. An output guardrail runs on the last agent, the one producing the final answer, and validates that result before it reaches the user. Everything between, including handoffs, runs unguarded because it is still the same protected run.

Figure 12. Guardrail placement. The input guardrail wraps the first agent, the output guardrail wraps the last, and the handoff in between runs inside the same protected run.

Putting It Together: A Complete Agent App

Four primitives, one Runner. Here is how the whole picture assembles into a single application you could actually ship: two specialists, a triage agent that routes to them, a tool, and guardrails at the edges.

The Whole System on One Page

Everything you have read across the last three pages composes cleanly. The triage agent declares its handoffs, each specialist owns its tools, and the input and output guardrails wrap the run. Nothing new is introduced here; the parts simply click together.

The diagram maps almost line for line onto the SDK. Specialists are agents with tools, the triage agent lists them as handoffs, and guardrails attach to the agents at the edges.

Section 4 · The Clarifier

How the Pieces Fit: MCP vs A2A vs an Agent SDK

Students confuse these three constantly, because the names all sound like "AI agent glue." They are not competitors. They solve different problems and are designed to work together. One small table fixes the confusion for good.

LayerConnectsExample in this course
MCPan agent to its tools and dataClaude Code + MCP (Module 11)
A2Aone agent to another agentGoogle A2A (this module)
Agent SDKbuilds a single agent applicationOpenAI Agents SDK (this module)
Figure 14. Complementary layers, not rivals. This is the link between M11 (MCP) and M12.
Figure 15. One system, three layers. The SDK builds the app, MCP gives each agent hands to reach tools and data, and A2A gives the app a voice to other agents.

Read It Left to Right

MCP is the agent-to-tools layer. It answers "how does my agent reach files, APIs, and databases?" You met it in Module 11. An agent with MCP can read a spreadsheet, query a database, or hit an API through a standard interface.

A2A is the agent-to-agent layer. It answers "how does my agent reach another agent that someone else built?" Different question entirely. MCP plugs an agent into tools; A2A plugs an agent into other agents. The two are complementary by design, Google explicitly positioned A2A as a companion to Anthropic's MCP, not a replacement.

An agent SDK is the build layer. It answers "how do I actually assemble one working agent application and ship it?" The OpenAI Agents SDK gives you Agents, Tools, Handoffs, and Guardrails to construct that app. Inside that app, individual agents might use MCP to reach tools, and the whole app might expose an A2A Agent Card so other systems can call it.

The mental model: an agent SDK builds the agent, MCP gives that agent hands to use tools, and A2A gives it a voice to talk to other agents. A production system often uses all three at once.

Section 4 · The Clarifier

When to Reach for Which

Knowing the three layers is one thing. Knowing which to reach for on a real project is another. The decision usually comes down to a single question about what needs to connect.

Figure 16. A decision guide. Match the layer to what must connect; large systems combine all three.

Rules of Thumb

  • Reach for MCP when a single agent needs to read files, query a database, or call an API through one standard interface.
  • Reach for A2A when a collaborator lives outside your codebase, built by another team or vendor, and must be discovered and delegated to.
  • Reach for an Agent SDK when you are assembling and shipping one application, wiring agents, tools, handoffs, and guardrails into a program you own.
  • In a production system these are not either or. The app is built with an SDK, its agents reach tools through MCP, and it exposes an A2A Agent Card so other systems can call it.

One question resolves most confusion: is the thing on the other end a tool, another agent, or the app itself? Answer that and the layer picks itself.

Section 5 · Wrap-Up

Module 12 — Key Takeaways

  • Platforms, not just models. The winners in AI build the coordination layer that connects agents, tools, and systems, and being able to work across those platforms is what makes you versatile.
  • A2A is the HTTP of agents. An open protocol (April 2025, now under the Linux Foundation) built on Agent Cards, Tasks, and transport over HTTP, SSE, and JSON-RPC, so agents from different vendors and frameworks can discover and collaborate.
  • The OpenAI Agents SDK has four building blocks. Agents, Tools, Handoffs, and Guardrails, driven by the Runner. Small surface area, fast to a working multi-agent app.
  • MCP, A2A, and an agent SDK are complementary. Agent-to-tools, agent-to-agent, and build-one-app. Real systems use all three together.

One-Page Cheat Sheet

The vocabulary of this module in one place. Skim it before the labs, and return to it whenever a term blurs.

A2A terms

  • Agent Card — JSON at /.well-known/agent.json listing skills, url, auth.
  • Task — the unit of work; moves submitted → working → completed / failed / canceled.
  • Transport — HTTP + JSON-RPC 2.0 + SSE for streaming.
  • Client / remote — the agent that asks vs. the agent that does the work.

Agents SDK terms

  • Agent — model + instructions + tools.
  • Tool — a Python function marked with @function_tool.
  • Handoff — one agent delegates the run to a specialist.
  • Guardrail — input / output check at the run's edges.
  • Runner — drives the agentic loop to a final output.
